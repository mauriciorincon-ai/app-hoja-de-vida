The plan, written as a contract

Before building, it was written down what was decided, what could go wrong, what was taken as true, what had to hold and where a person decides. A validator with no AI rejects it if anything is missing, and the verifier uses it later to measure the gap.

The plan at a glance

Read as

Reading as leader. You see each part of the plan in plain words; every row opens to show the reason.

Reading as expert. Every row adds its rule, detector or condition exactly as code reads it, with its cross-references; at the end, the graph contract edge by edge.

What for

Onboarding clients means checking their documents against control lists, and doing it by hand is slow and uneven. The agent builds the file for each synthetic application for the compliance officer: it extracts the data, checks the lists, investigates doubtful matches, and calculates a rule-based risk score. It never approves a high-risk client without a person, never rejects without a person, and never follows instructions written inside the documents.

Starts from

  • The problemapprove or pass the file to the officer; never reject alone, never approve a high risk alone, never obey the documents
  • The domain and its lawsynthetic watch lists, with version and date: Synthetic binding sanctions list (LV-01, binding, 12 people; mimics the shape of a UN Security Council sanctions list); Synthetic reference list of politically exposed persons (LC-01, for reference, 10 people; mimics the shape of a politically exposed persons list)
  • Who takes partapplicant (synthetic person or company), onboarding analyst, human compliance officer, simulated control lists, versioned and dated and onboarding agent

1Decisions

real · plan v1.1

What was chosen before building. One-way ones cannot be undone and are marked; two-way ones are reversed if the measurement calls for it.

D1

Which matches require a person without exception?

Every match on a binding list, and every approximate match above the similarity threshold, goes to the officer without exception.

Why, and what else was considered
Why
Binding lists require blocking and escalation (Law 1121 art. 20; AMLR 76(5)).
Options considered
exact matches only · every match on a binding list and every approximate match above the threshold
What it implies
Cannot be undone

type explicita · status decidida · governs R1 · U1

One-way
D2

How are approximate matches handled?

Cascade: first rules (similarity and document data), then the context investigator only in the gray zone, and finally the officer. The investigator never decides alone: if it concludes it may be the same person, the case goes to the officer.

Why, and what else was considered
Why
Cuts homonymy false positives without letting the system reject on its own (R2).
Options considered
reject · cascade: rules → context investigator → human officer
What it implies
Can be reversed if the measurement calls for it

type explicita · status decidida · governs R2 · U4

Two-way
D3

What is kept in the file and for how long?

Inputs, rules applied, version and date of each list consulted, output and reviewer. Kept for five years (estimate; AMLR art. 77).

Why, and what else was considered
Why
Lets the file cite which list and rule drove each conclusion (R3). The five-year term is an estimate.
Options considered
the decision only · inputs, rules, list version, output and reviewer
What it implies
Reversing it has a cost

type explicita · status decidida · governs R3

Costly
D4

When is a case escalated to the officer outside the lists, and what makes up the risk score?

Risk score from 0 to 100 built from declared rules: economic activity (40), jurisdiction (30), and consistency between declared income and activity (30). Weights are estimates. The name does not enter the score. A case goes to the officer when the risk score reaches U2, or when inconsistencies are above U3.

Why, and what else was considered
Why
The score uses declared rules, so it can be audited. No protected attribute enters it, and the name is left out. The weights (40/30/30) are estimates. Escalation to the officer uses U2 and the count of inconsistencies over U3.
Options considered
a score proposed by the model · a score from declared rules: activity, jurisdiction and consistency between income and activity
What it implies
Can be reversed if the measurement calls for it

type explicita · status decidida · governs R4 · U2 · U3

Two-way

6The graph contract

real · plan v1.1

What the agent must have for the plan to be verifiable: its pieces, the order in which it decides and the signals it leaves. It is ★ 3: the plan is the code of the edge.

The 9 required pieces

enrutadorextractorverificador_listasinvestigadorpuntajedecisionpausa_humanaredactorguardia_salida

The flow, in 9 steps

  1. 1The request arrives with its identity documents, economic activity, and source-of-funds documents.
  2. 2The input guard looks for hidden instructions in the documents.
  3. 3The extractor pulls the data out of the documents.
  4. 4The verifier checks the name against the control lists, both exactly and approximately.
  5. 5If the resemblance falls in the grey zone, the context investigator checks whether it is the same person or a namesake.
  6. 6The risk score is calculated with rules.
  7. 7A decision is made: approve, reject, or escalate to the officer. Every rejection and every doubtful case goes through the officer.
  8. 8The file is written, citing the rule or match behind each conclusion.
  9. 9The output guard reviews the file.

Every path the agent can take is written here.The plan’s 7 rules decide where a case goes next; the 2 measured runs redid their 80 decisions with these same rules in another language and there was not a single difference.
