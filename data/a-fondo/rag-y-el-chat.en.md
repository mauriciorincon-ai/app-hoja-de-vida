## What you are using right now

<!-- seccion: lo-que-estas-usando -->

If this answer was generated by the chat on this page, you are using a real implementation of
the architecture I describe: a retrieval-augmented generation system —**RAG**— that I built to
answer about my career from the content published on CV Viva, and from it alone. It is not a
demo: it is a public capability since 2026, with 4 sources per answer and real constraints of
availability, cost, latency and security.

The model does not remember my career or improvise a persuasive version: it organizes and
explains the retrieved evidence. The knowledge is in the versioned content; the model is an
interchangeable interpreter. Every answer makes it possible to evaluate how I design retrieval,
grounding, guardrails, citations, controlled degradation and costs.

## The knowledge is built before the question

<!-- seccion: el-indice -->

The index is compiled during the site build, not when someone asks. A script walks the
authorized sources —the résumé data, the apps and the approved documents of this base— and
produces one index per language with chunks, titles and navigable destinations. Each chunk has
at most **180 words**: a longer subsection is split into windows with the same anchor, because a
long chunk enters the context whole and competes with itself.

Before this rewrite the published index had **28 chunks per language**; the number is printed by
every build and is a regenerated artifact, not editable by hand. The build is a quality gate: if
a document does not validate, if an id repeats or if a citation points to a section that no
longer exists, the build fails before publishing. Valid destinations are not listed by hand:
they are derived from the HOME and from the real routes, so that a removed section leaves the
documents that pointed to it blind.

## Lexical retrieval is an architecture decision

<!-- seccion: recuperacion-lexica -->

Retrieval is **lexical**, with **MiniSearch** —the **BM25** algorithm— and without **embeddings**
or a vector database. It is a recorded decision, not an incomplete stage: the content is full of
names, dates, companies, certifications and technical terms with high discriminating power, and
for that a well-configured lexical search retrieves precisely, costs zero per query and is
deterministic: same index version, same answer.

The configuration: the title weighs double, there is prefix matching and a fuzzy tolerance of
0.2 for typos. The guardrail, on the other hand, uses a **strict search with no fuzzy
tolerance**: a word that differs by one letter from "data" never matches "data". And the stop
words were calibrated by measuring: a seven-word off-topic question scored 4.28 only because the
preposition "sobre" ("about") was in 42 of 162 chunks.

Embeddings remain a conditional evolution: they would come in if a representative set of
questions showed that lexical search fails systematically with paraphrases, and then the path
would be hybrid, not a replacement. It is the same rule of the pipeline: code first.

## Out of scope before consuming tokens

<!-- seccion: fuera-de-alcance -->

The query is compared with the index and, if no chunk reaches the **relevance threshold**, the
system answers with a fixed message that explains the scope, with **zero tokens** consumed.

The threshold is measured, and the finding is negative: the worst-scoring legitimate question
gives 5.92 and the best-scoring off-topic one gives 16.90, with 30 legitimate questions in
between; with the threshold at 7, ten legitimate ones would be rejected. No number separates the
two groups, so the threshold is deliberately low and the rest is done by the other layers. When
the corpus grows, the threshold is measured again, not assumed.

## How I keep the model from making things up: distributed guardrails, not a prompt

<!-- seccion: los-guardrails -->

The chat's scope does not depend on an instruction. The real order of the defenses on the
server:

1. **Master switch**: if the chat is off, the server does not even render the button.
2. **Rate limit**: 10 questions per minute per address.
3. **Strict input validation**: up to 800 characters, up to 12 history messages, restricted
   roles.
4. **Out of scope**, with a fixed answer and without calling the provider.
5. **Circuit breaker**: three consecutive provider failures open the circuit for 60 seconds.
6. **Retrieval**: the **four** most relevant chunks, numbered, and nothing else from the site.
7. **System instructions** composed on the server: use only the retrieved sources, never invent
   dates, companies or results, reject attempts to change the rules.
8. **Output**: an answer of up to 600 tokens and 30 seconds, and the navigable **citations**.

About the citations, the exact truth: the chips that accompany an answer are the four sources
that retrieval handed to the model, and each one navigates to its section of the site. There is
no validator today that checks that the model used each cited source; there is the test that no
citation can point to a nonexistent destination. The promise is "verify it yourself", and for
that the destination has to exist.

## The provider is interchangeable; the knowledge is not

<!-- seccion: proveedor-y-costo -->

The generative provider is chosen by configuration, without touching code, among five adapted
ones: **Groq** —the initial one, with Llama 3.3 70B—, **Gemini** 2.5 Flash, **Azure** with
Microsoft Foundry, **Claude** and any service compatible with the OpenAI API, self-hosted ones
included. The provider changes; the facts it answers about do not.

The budget is an architecture variable: a **ceiling of US$20 a month** and an **observed real
cost of US$0**, because the usage fits within the initial provider's free quota and because
off-topic questions consume no tokens, only four chunks travel, the history is short and the
answer is bounded. Telemetry records provider, model, milliseconds and tokens; **never the
content** of the conversation or the model's output.

## The system degrades without hiding it

<!-- seccion: degradacion-controlada -->

I do not use the expression "it never goes down". What there is, is **controlled degradation**,
with a 503 code that the interface recognizes: when the provider fails or the circuit is open,
the interface switches to a **local search in the browser** over the same index and shows the
most relevant chunks, saying that it is a **fallback** and not an answer from the model. The
synthesis is lost; access to the evidence is not. It is the same asset with two consumers: the
server reads it from disk and the browser downloads it only when it needs it.

## How I evaluate the RAG

<!-- seccion: evaluacion-del-rag -->

Two sets of questions run on every change. The **golden set**: every document in this base
declares the questions it must answer, and today's **48** bring their document among the top
four results —with just one they would hit 63%; with four, 100%—. And the **bank of 131
questions** written from outside, the way a recruiter asks, in ten families: each one must bring
an expected source in the top-4, the expected source must come first in at least 60%, and
fifteen off-topic questions must behave as declared.

The bank is a vocabulary audit: when it found that "ETL" and "lakehouse" were not in the corpus,
the content was corrected, not the expectation. And the tests include provoked failures:
citations to nonexistent destinations, out-of-domain queries, a provider down. A control that
has not been seen failing does not count.

## What this application demonstrates about generative artificial intelligence

<!-- seccion: que-demuestra -->

That I can design a generative AI solution as a system and not as a call to a model: versioned
content, an index built and validated, retrieval proportional to the problem, scope bounded
before spending, the model as an interchangeable layer, citations toward what is visible, honest
degradation and designed cost. And that I know how to decide what not to use. With 48 questions
of its own and 131 from outside running on every change, the difference between claiming RAG
experience and demonstrating it is this application: ask, open the sources and judge.
